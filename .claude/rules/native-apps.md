# Native apps (`apps/`)

`apps/` is a **separate Cargo workspace** with its own `Cargo.lock` and `rust-toolchain.toml`. It is separate so its UI dependencies can never change the root lockfile, which fixes the contract and delegate WASM bytes and so their keys. `cargo make` tasks and `build.yml` do not build it; `.github/workflows/apps.yml` does.

| Crate | Role |
|---|---|
| `apps/river-app` | UI and setup state machine, shared by every platform |
| `apps/desktop` | Desktop shell (binary `river`), including the Freenet installer, which verifies the release's signed checksums |

```bash
cd apps
cargo test --locked                  # unit tests
cargo run -p river-desktop           # the app
cargo run -p river-desktop -- --list-scenes
cargo run -p river-desktop -- --snap out.png --scene not-installed   # headless render
cargo run -p river-desktop -- --snap out.png --scene chat-narrow --size 820x720
```

The window opens at 1280x800 and shrinks to 640x480. Every screen, setup included, uses one dark palette (`apps/river-app/src/chat/style.rs`); there is no light theme yet. A scene cannot set the window size, so the `*narrow*` scenes need `--size 820x720` to render as CI renders them (`scene_size` in `apps/river-app/src/lib.rs`, checked against `apps.yml` by a test).

Linux builds need `libxkbcommon-dev` and `libwayland-dev`. At run time Rune also `dlopen`s `libfontconfig.so.1` for system fonts (`libfontconfig1`; no build package needed): without it the app starts and draws (checked by hiding the library in a mount namespace), with fewer fallback fonts. The Linux tarball README names it. Headless renders without a GPU need a software Vulkan driver: install `mesa-vulkan-drivers` and point `VK_ICD_FILENAMES` at its `lvp_icd*.json`.

## Settings

One dialog, opened by the gear in the room list header or Ctrl+, (Cmd+, on a Mac): `apps/river-app/src/chat/settings.rs`. A list of sections on the left and the open section on the right; below `NARROW_WIDTH` the list is its own screen and a section opens with a Back button. A section is an entry in `Section::ALL` plus an arm in `section_content`, and exists only when it has content. Today: Updates (`update_view::updates_section`), Notifications (`notifications_section` in `settings.rs`: the do not disturb group `dnd::dnd_group` with its true-by-construction state line `Settings::state_line`, and the "Show the sender and text in notifications" switch), Background and startup (`background::background_section`, listed only when the shell passes a `BackgroundHost`; without a tray the keep-running switch is left out; Quit River is a danger button below the switches) Connection (`connection_section` in `settings.rs`), Identity (`identity_section`: "Import identity..." opens the Import identity dialog; "Export identity" lists every room, each with an Export button that opens the Export identity dialog for that room via `Chat::open_export_for`; the Join dialog also has an "Import it" link, key `join-import-id`) and Appearance (`appearance_section`: Size buttons for the `zoom::STEPS`, keys `settings-size-{percent}`, set through `Zoom::set` and saved like Ctrl+=, and a button that opens the keyboard shortcuts page). These sections close Settings first, then open the existing dialog. The room list keeps one quiet "Do not disturb: on/off" row (key `dnd`): it flips the switch, or opens Settings > Notifications when the daily schedule is what has it on. Per-room notification choices stay on each room's bell; there is no global notifications switch. Saved choices keep their keys and formats: `do_not_disturb` (`dnd::Settings` JSON, saved once typing pauses or the section is left) and `notification_previews` (a bool, `chat::PREVIEWS_PREF`, default false); both are per device and neither is in the writes table below. The last section shown is not saved. Every control in Settings acts at once, so the dialog has no Save or Close button; keep element keys (`settings-section-*`, `settings-auto`, `settings-node-*`) stable, the tests and `fresh_node_e2e.sh` find them. The status pill ("Node status") and the node entry under it stay where they were. The room list footer no longer has Import ID, the members panel no longer has Export ID and the room list heading no longer has the "?" button; Ctrl+/ still opens the shortcuts page.

Linux Ctrl+Right/Ctrl+Delete follow Rune's word rule (start of the next word); an end-of-word override was tried (river#957, closed): it cannot scroll the caret into view nor match Rune's undo records from outside Rune; revisit when Rune has a forward-word-rule setting.

## How river-app reads rooms

Once setup connects, `src/rooms/` reads the user's rooms from the local node:

1. It asks the node for the River web app's identity through a user-approved app grant (freenet-core v0.2.156+).
2. It reads the rooms stored in the chat delegate and subscribes to each room contract.
3. When the node has no chat delegate, it registers the one it carries, as the web UI does since #757 (list first, register on a missing delegate). It does this only on the grant connection: the node records, for good, the identity a delegate was first registered under.
4. Once a run, it carries the user's rooms over from the earlier chat delegates `legacy_delegates.toml` lists (`src/rooms/carry.rs`, #889), reading each as the web UI's walk does (the listing, the raw key index twice, `rooms_meta`, the rooms it names): newest first, the newest generation holding a slot for a room the current delegate does not hold decides (a room or a tombstone), and it is added by the compare-and-swap below, only where the key holds nothing, with that generation recorded in `rooms_meta.identity_sources` so the web UI's ranked merge still lets a newer generation win. A generation that can't be read (an error, no answer, a key index that does not add up) STOPS the walk: nothing older decides anything, since that generation may hold a newer copy or a tombstone; a slot that does not decode holds its room back the same way. A user's create, join or leave goes ahead of the walk at its next request. The room list shows the walk while it runs, and what was left behind, with Try again. It never writes freenet-migrate's journal or markers, so the web UI's journaled walk (#763) still runs as before and folds in what only it does (older generations' other fields, the room order, `rooms_data`, `outbound_dms`, which stay in the earlier delegate for a desktop-only user).
5. A stored room whose contract key is one of its owner's earlier room-contract keys (`common/legacy_room_contracts.toml`) is followed under the key this build's room contract gives it (`src/rooms/rekey.rs`). When that key answers `NotFound` (only then), the room is followed under its earlier key again while the app moves it: freenet-migrate's `ProbeDriver` folds every earlier key down to the stored one into the app's copy (FoldAll, as the web UI's `start_rekey_merge`) and PUTs it under the current key; when every earlier key answered with nothing, the app's own copy is PUT, as the web UI seeds it. A move that did not end well is tried again after a wait that doubles; keys that did not answer are folded in later. A join or an ID import whose room is not under the current key reads the earlier keys newest first (for at most 3 minutes) and PUTs the newest real state before it goes on. A read of an earlier key that goes unanswered is passed over without a new connection.

A room the app stores does not hide older rooms from the web UI. The web UI's journaled walk (#763) carries them forward whatever the current delegate holds (`src/rooms/work.rs` has the details).

The chat screen (`src/chat/`) shows the rooms. Snapshots and tests use built-in example data (`chat::Source::Example`). Colours and sizes follow the web UI in `ui/`.

## What river-app writes

| Write | Where | Guard |
|---|---|---|
| Messages, replies, edits and deletions of own messages, reactions | Room contract UPDATE, built and signed as the web UI does | `src/rooms/outbox.rs` |
| Direct messages (text), each an UPDATE of the room contract, composed and signed once with the room's `self_sk` and sent as raw UTF-8 like the web UI | `src/rooms/dm_send.rs`, `src/rooms/outbox.rs` |
| The text of a direct message it sent, as an entry of `outbound_dms` (add on send; remove on discard of a saved one, and remove when the recipient's purge envelope names the message's token, `prune_purged_texts`) | Chat delegate, by a compare-and-swap that re-reads the key, edits only the `entries` array of the CBOR it found (the archive list and unknown fields are carried over) and stores at the generation it read. Never before the key was read and decoded, or listed as absent by a trustworthy list (a list that named rooms) on a first save to a node that never had the key; never over a value it cannot decode or one that vanished after it was read; never while River has moved on; at most 4 MiB. Retried on its own with a wait that doubles, a bounded number of times | `src/rooms/dm_save.rs`, `src/rooms/dm_store.rs` |
| The archive list (`hidden_threads`) of the same `outbound_dms` value: archiving, un-archiving, sending into an archived thread (which un-archives it), and dropping the entry when the peer has written past its cutoff | Chat delegate, by the same compare-and-swap as the sent text but in a write of its own (so a store that refuses one cannot refuse the other, and each has its own waits and failure count), which edits only the entries of the thread it names in `hidden_threads` (a new entry, a raised `hidden_at_ts`, or a removal; the entry's other fields, the other entries, `entries` and unknown fields are carried over) and refuses on the same terms (unreadable, vanished, 4 MiB, not hydrated, River moved on). The key is the room's owner key and the peer's FULL member id, as the web UI stores it. Owed until a write ends well, kept over every read meanwhile (and a read that began before the write ended does not undo it), retried like the saved text. When the write found the store already as asked or at a higher cutoff (another device), the stored rooms are read again. The web UI's blind save can put an older list back: the thread then shows on the rail again and is not fought | `src/rooms/dm_archive.rs`, `src/rooms/dm_store.rs`, `src/rooms/dm_save.rs` |
| A deletion of the messages someone sent the user ("Delete their messages"): one signed purge envelope, an UPDATE of the room contract (`ContractRequest::Update` with `advanced_purges`) | Built only by river-core's `advance_recipient_purges` from the envelope the room holds when it goes out (a later one that omits a held token would lift that tombstone, and the message could come back). Built again while unsent and when a refused or unconfirmed one is retried, sent again byte for byte while out or unanswered. Refused for a room not yet read from the network and over the 1000-token cap; only messages from that person to the user are named. Not repaired when another device deletes at the same moment (see below) | `src/rooms/dm_purge.rs`, `src/rooms/outbox.rs` |
| An invitation sent in a direct message ("Share invite" in the member dialog): the user's own `Invitation` to another room (`create::mint_invitation`, the same one the invite link carries) in a `DirectMessageBody::Invite` (`encode_body`, `0x80` + CBOR), sealed and signed as any direct message and queued through the same path, so retry resends the identical bytes. The sender's row is the web UI's summary string `[Invitation]` + the trimmed note, saved like a sent text (the `outbound_dms` compare-and-swap write above, holding only that string) | The invitation is a bearer credential (the invitee's signing key and, for a private room, its secrets): it exists only inside the sealed envelope and, briefly, in memory while sending or accepting; its buffers are wiped, no action, view model, cache entry or message prints it, and nothing logs. The view model keeps only a room key, a label and a bounded, cleaned note. Refused for a room the user cannot write in or is not listed in, a note over 4000 characters or with hidden or reordering characters, and while River has moved on | `src/rooms/dm_invite.rs`, `src/rooms/dm_send.rs`, `src/rooms/outbox.rs` |
| Accepting an invitation received in a direct message (the card's Accept) | Joins through the join work a pasted invite code uses (`Work::join_invitation`), whose own writes are the room UPDATE (the join event and member records) and the chat delegate's room store and `rooms_meta` (the join rows above), and nothing else. The background work reads the invitation again from the message (by purge token) when Accept is pressed: the message must be the room's, to the user, signed by the person the thread names, within the bounds, and the invitation must name the room the message names, and agree with itself; the join must add a NEW member (an invitation for a key the room already holds is refused, or a member could hand the user that member's identity in the room). Member ids are per room, so the invitation's inviter cannot be compared with the message's sender. The default nickname the join dialog offers is used. Never automatic; refused for a room already in the list and while a join of it is under way, and while River has moved on. The card says who SENT the message | `src/rooms/dm_invite.rs`, `src/rooms/work.rs` |
| A room it creates | Seed PUT under that room's own contract | `src/rooms/create.rs` |
| A room moved across a room-contract re-key: every earlier key down to the stored one folded into the app's copy (a join or an ID import: the newest earlier key that holds the room), or the app's copy alone when no earlier key holds it; upgrade pointer stripped, normalized | PUT under the room's current key, only after that key answered `NotFound` (to the subscribe, or to a join's or ID import's read); tried again with a growing wait. Earlier keys are only read, never written | `src/rooms/rekey.rs`, `src/rooms/work.rs` |
| Rooms and tombstones carried over from earlier chat delegates, then the deciding generation of each room in `rooms_meta.identity_sources` | Chat delegate, by the same compare-and-swap as a new room, as `NewRoom` (the fields the drift tests pin as decodable by the web UI) plus the slot's `previous_contract_key` and `rekey_merge` when they read as the web UI reads them, only where the key holds nothing; `rooms_meta` edited only in `identity_sources`, every other field kept. Earlier delegates are only read (`ListRequest`, `GetRequest`), never registered or written | `src/rooms/carry.rs`, `src/rooms/work.rs` |
| Joining from an invitation | UPDATE (the web UI PUTs instead); after a room-contract re-key whose current key has no state yet, first the PUT of the room moved from an earlier key (row below) | `src/rooms/work.rs` |
| New or joined room | Chat delegate, by the web UI's generation compare-and-swap (`GetVersionedRequest`, then `CasStoreRequest`, re-read on conflict). Only ADDS a room where the key holds nothing, or a tombstone when joining | `river_core::stored_rooms` |
| `rooms_meta` | Chat delegate, changing only the open room, a room's notification mode, a left room's entries, or (carrying rooms over) `identity_sources` | `river_core::stored_rooms`, `src/rooms/carry.rs` |
| Each room's signing key (`self_sk`) | Delegate `signing_key:` namespace, only when the delegate holds none. Never replaces a key. Lowest priority, one request at a time, backed off on failure | `src/rooms/keys.rs` |

Direct messages raise OS notifications in this app (the web UI raises none); what they say, when, and the privacy default are in `direct-messages.md`, "Native app notifications".

Direct messages are addressed by the recipient's FULL member id (`MemberId`, 64 bits), never by `MemberId`'s `Display` form, which is a 40-bit label a member can grind to match another's. A sent DM cannot be read back by its sender (it is sealed to the recipient), so the sent text is saved to the delegate's `outbound_dms` key as soon as the DM is queued. The web UI saves that whole key with a blind store from its own copy, so a web tab that loaded before a native save can overwrite it: the app notices when a read no longer holds an entry it saved and saves it again (at most 3 times per message, and only while the message is still in the room, from the user's current identity there, and not purged). It cannot prevent the overwrite. The web UI's archive list (`hidden_threads`) lives in the same value: a text write never changes it, and an archive write changes only the thread it names (see the row above).

The room keeps ONE purge envelope per recipient, and when the node answers Ok the app applies the delta to its own copy of the room. If another device signed in as the user has signed a higher-version envelope that this copy has not seen yet (the copy lags the node), the node drops ours, the thread shows the messages gone, and they come back when the other envelope arrives, so those messages can come back if a peer offers them again. The window is however long the copy lags the node, not one moment. The web UI and `riverctl` repair this for what they deleted, from a record kept with the room (`own_purges`). The native app does NOT: that record is a field of the stored room that this app does not read or write, and a new delegate key would change the delegate's migration, so persistent healing needs its own design. The confirmation dialog says: "If another device signed in as you has deleted messages recently, some messages can come back." When a recipient's envelope names a token of a message the user sent, the app drops its saved text for it from `outbound_dms` (an entry removal in the same compare-and-swap write, `DmOp::Remove`; never because a message is merely absent from the room, and also for text a save is adding at that moment, removed after the save).

In the chat delegate its writes are the rows above: the stored rooms and `rooms_meta`, the signing keys, and `outbound_dms` (adds and removes of its own entries, and changes to the archive entries of one thread). The web UI writes the delegate at the same time. The `stored_rooms_drift` tests in `ui/src/room_data.rs` pin the bytes it stores to the web UI's types.

Anything the app stores in the chat delegate must stay decodable by the web UI builds in use, or their migration walk stops on every load.

When a pointer record names a generation newer than the WASM the app carries, the app stops writing and asks the user to update (`apps/river-app/src/rooms/generation.rs`).

## The update key

The public key River's self-update trusts is committed in `apps/desktop/update-pubkey.hex` and compiled into each release build; `.github/workflows/release-desktop.yml` reads it into `RIVER_UPDATE_PUBKEY_HEX` for the Build step and the tag check compares the built binary's key with the file. The repository variable of that name is no longer used. Rotating the key is a new release: `update_tool keygen`, commit the public half by reviewed PR, keep the private half in `~/.freenet-signing` and 1Password. `build.rs` deliberately has no fallback to the file (tests and `apps/scripts/update-ci.sh` build with their own or no key).

## What it shares with the root workspace

It depends on `river-core` (`common/`) by path, with the client-only features `ecies-randomized`, `ecies-client`, `mentions`, `stored-rooms`, `invitation` and `migration`. A change under `common/`, or to the root `Cargo.toml` (river-core inherits versions from it), runs `apps.yml`.

It compiles in three `ui/` files with `include_bytes!`. An edit to any of them runs `apps.yml`; nothing else under `ui/` is read by `apps/`. It also compiles in two registries from the repository root with `include_str!`: `pointer-records.toml` and `legacy_delegates.toml` (the earlier chat delegates it carries rooms over from); `apps.yml` runs for both. The earlier room-contract keys come from river-core's `migration` feature (`common/legacy_room_contracts.toml`).

| File | Why |
|---|---|
| `ui/assets/river_logo.svg` | The logo |
| `ui/public/contracts/chat_delegate.wasm` | Its hash is the delegate key the app reads rooms from |
| `ui/public/contracts/room_contract.wasm` | Its hash is part of every room's contract key |

A test checks that its `freenet-stdlib` (the client API's wire format) is the version river-core resolves to in the root `Cargo.lock`.

`apps/Cargo.toml` and `apps/Cargo.lock` cannot change a contract or delegate key. The WASM is built from the root workspace with the root `Cargo.lock`, and the apps' lockfile is never consulted there, even though `apps/river-app` depends on `river-core` by path (see the note in `apps/Cargo.toml`). Every client-only feature it enables must stay off for the room-contract and chat-delegate builds.

## How to bump Rune

Rune is pre-release, git-only and moves about 70 commits a day. `apps/Cargo.toml` pins one rev of its `dev` branch (never rewritten, so a revert is one line) in `rune`, `rune-kit` and six `[patch.crates-io]` entries. One bump per PR, never mixed with other work.

When: when a feature we need lands, otherwise about monthly. Waiting a quarter means reading about 2,000 changelog entries.

1. Pick the new rev: `git ls-remote https://github.com/anomalyco/rune dev`. Record the old and new in the PR body. Check the old rev is an ancestor of the new (`git merge-base --is-ancestor`).
2. Read what changed since the pin. Get a checkout of Rune first: `git clone https://github.com/anomalyco/rune` (or build once so it is under `~/.cargo/git/checkouts/rune-*/`). `changelog/unreleased/` is where entries live; `CHANGELOG.md` is folded rarely. List new entries with `git diff --name-status <old> <new> -- changelog | grep ^A` and grep them for `dialog`, `modal`, `focus`, `scroll`, `ime`, `text`, `word`, `chord`, `windows`, `tray`, `a11y`. "Breaking", "no longer" and "replaces" mean a compile or behaviour change.
3. Change every rev in `apps/Cargo.toml` together. Re-read the `[patch.crates-io]` table in Rune's own `Cargo.toml` at the new rev: add, drop or rename entries to match (a crate Rune uses as a path dependency, such as `tiny-skia-path`, is not patched). `rune_revs_agree_in_apps_cargo_toml` fails if the revs differ, are not 40 hex digits, or an entry is not a `git =` entry. Then regenerate the lock WITHOUT `--locked`: `cd apps && cargo metadata --format-version 1 >/dev/null` (this is what regenerated the lock for the eff95e80 bump), commit `apps/Cargo.lock`, and only then check `cargo metadata --locked` from a fresh clone of the branch and once with an empty `CARGO_HOME`.
4. Look at what the lock changed: `git diff apps/Cargo.lock | grep '^[+-]name'`. List crates added and removed, note which have build scripts (`cargo metadata` shows `custom-build` targets) and whether any crypto or network crate changed version. Check for new system libraries: `ldd target/debug/river` and `strings target/debug/river | grep '\.so\.'` (Rune `dlopen`s some, such as libfontconfig). Add any to the tarball README and the Linux paragraph above.
5. Fix compile errors on Linux and with `--target x86_64-pc-windows-gnu`; read the macOS `cfg` code by hand, since nova cannot build it.
6. Run `cargo test -p river-app -p river-desktop`, clippy with `-D warnings` on both targets, `cargo fmt`, and `apps/scripts/fresh-node-e2e.sh`. The `rune_bump` tests in `chat/tests.rs` pin what the app does through Rune features (word motion per platform, IME with popups, undo, focus after dialogs, the Ctrl+Shift direction chord): a changed line means Rune changed, so read its changelog before editing the expectation.
7. Before touching a failing test, run it on the old pin to confirm it passed there, then decide whether Rune or River is right from the changelog entry and what a user expects. Update the test with an explanation or fix River's code; never weaken the assertion.
8. Pixel ratchet: `apps/scripts/scene-fingerprints.sh check` on the machine that made `scene-fingerprints.json` (not CI), then `update` in the bump PR if the pixels moved and say so.
9. Scene diff: render every scene (`river --list-scenes`; `--snap out.png --scene NAME --scale 1`, `--size 820x720` for `*narrow*`) with a binary built at the old pin and one at the new, compare pixel by pixel, and look at the differing scenes before and after. Look specifically at the field fill and the focus ring of a dialog input, and measure the ring's contrast against the field and the dialog (at least 3:1). Describe what moved in the PR. Whole-screen 1 px shifts and glyph anti-aliasing changes are expected; a missing, overlapping or clipped element is not.
10. Open the PR as a draft, run the full review (UI plus dependency change), and merge it alone. Features that use the new rev come in later PRs.
